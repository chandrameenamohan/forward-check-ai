## Architecture Overview

### Pipeline Flow

```
Telegram Message → Classifier (Haiku) → Claim Strategist (Opus 4.6)
  → 2-3 Parallel Investigators (Sonnet 4.5) → Devil's Advocate (Opus 4.6)
  → Judge (Opus 4.6) → VerdictFormatter (code) → Telegram Reply + Web Page
```

### Key Modules

| Module | Location | Responsibility |
|--------|----------|---------------|
| Bot | `src/bot/` | Telegram bot, message handling, status updates |
| Server | `src/server/` | Express server, health endpoint, verdict pages |
| Database | `src/db/` | SQLite connection, investigation repository, feedback repository |
| Schemas | `src/schemas/` | Zod schemas for all agent I/O |
| Services | `src/services/` | Claude client wrapper, claim cache, URL extractor |
| Agents | `src/agents/` | Agent implementations (classifier, strategist, investigators, DA, judge) |
| Tools | `src/tools/` | Search tools (Brave, Google Fact Check) |
| Orchestrator | `src/orchestrator/` | Pipeline orchestration, agent runner, tool-use loop |
| Formatter | `src/formatter/` | Platform-agnostic formatting (confidence gates) |
| Platforms | `src/platforms/` | Platform abstraction layer (types, adapters, responders) |
| Config | `src/config/` | Environment config, logger setup |

### Data Flow

1. User forwards message to Telegram bot
2. Bot saves to SQLite, sends "Investigating..." status
3. Orchestrator runs pipeline:
   a. Classifier (Haiku) → ClassifierResult
   b. Claim Strategist (Opus 4.6) → SearchStrategy
   c. 2-3 Investigators (Sonnet 4.5) in parallel → AgentReport[]
   d. Devil's Advocate (Opus 4.6) → ChallengeReport
   e. Judge (Opus 4.6 + brave_web_search) → FinalVerdict
4. VerdictFormatter produces Telegram HTML + saves to DB
5. Bot sends verdict with "View Full Analysis" link
6. Web server renders `/v/:id` verdict page

## Coding Standards

- **Strict TypeScript** — `strict: true` in tsconfig, no `any`
- **ESM modules** — `"type": "module"` in package.json, `.js` extensions in imports
- **Max 400 lines per file** — extract if larger
- **No `console.log`** — use Pino logger from `src/config/logger.ts`
- **Zod for validation** — all agent I/O validated through Zod schemas

- **Test isolation** — each test independent, no shared mutable state
- **Parameterized SQL** — never interpolate user input

## Gotchas

- **Zod v4 installed (4.3.6):** The `z` import and API (`z.object`, `z.string`, `z.enum`, etc.) are compatible with the spec's schema definitions. Import as `import { z } from "zod"`.
- **Express v5 installed (5.2.1):** Express 5 is the latest major. Router API is mostly the same as v4 but `req.params` returns `Record<string, string | undefined>` and error handling has minor differences.
- **Zod v4 `.default()` + `.transform()` ordering:** In Zod v4, `.default()` placed AFTER `.transform().pipe()` returns the raw default value without running the transform. Place `.default()` BEFORE `.transform()` so the default feeds through the pipeline. Example: `z.string().default("3000").transform(val => parseInt(val, 10)).pipe(z.number())`.
- **dotenv v17 logs injection messages to stdout:** `dotenv@17.2.4` prints "[dotenv@17.2.4] injecting env (N) from .env" on every `config()` call. This is cosmetic noise in tests but harmless.
- **SQLite `datetime('now')` has second-level granularity:** Rapid sequential inserts get identical `created_at` values, making `ORDER BY created_at DESC` non-deterministic. Use `ORDER BY rowid DESC` for reliable insertion-order sorting.
- **Vitest 4 `it()` options API:** Vitest 4 removed the `it(name, fn, { timeout })` 3-arg signature. Use `it(name, { timeout }, fn)` or `it.skipIf(cond)(name, { timeout }, fn)` instead. The old pattern was deprecated in Vitest 3.
- **Anthropic SDK adaptive thinking effort:** Effort levels (`low`, `medium`, `high`, `max`) are on `output_config.effort` in `MessageCreateParamsBase`, NOT on `ThinkingConfigAdaptive`. `ThinkingConfigAdaptive` only has `{ type: "adaptive" }`. For agents that need different effort levels, set `output_config: { effort: "high" }` alongside `thinking: { type: "adaptive" }`.
- **Tool-use for structured output pattern:** For agents with complex nested output schemas (like Strategist), use a `submit_*` tool instead of instructing JSON text output. Tool-use inputs are already structured objects — no JSON parsing or markdown-fence stripping needed. The model calls the tool with structured data, and you validate with Zod directly. More reliable than text-based JSON for deeply nested schemas.
- **Grammy bot testing pattern:** To test handlers without a real Telegram connection: 1) Set `bot.botInfo` to a fake `UserFromGetMe` object after creating the bot. 2) Use `bot.api.config.use((prev, method, payload) => ...)` to intercept outgoing API calls (e.g., `sendMessage`). 3) Call `bot.handleUpdate(update)` with a manually constructed `Update` object. No external test libraries needed.
- **Agent runner `outputConfig` for effort levels:** `runAgent` now accepts `outputConfig?: { effort: "low" | "medium" | "high" | "max" }` which is spread as `output_config` into `client.createMessage()`. Use this when an agent needs adaptive thinking effort levels through the multi-turn loop (e.g., Judge with effort "max"). Previously, agents needing effort levels had to call `client.createMessage()` directly (like DA), but the Judge needs both multi-turn tool use AND effort control.
- **Agent runner loop continues after submit_* tool calls:** `runAgent` processes `submit_report`/`submit_*` tools like any other tool call — executes the callback, pushes tool result to messages, and loops again (since `stop_reason === "tool_use"`). The loop only breaks on `end_turn` or when maxTurns is exhausted. In tests, always add an `END_TURN_RESPONSE` mock after the `submit_*` mock, or rely on maxTurns to terminate. The real API will naturally end after receiving the tool result acknowledgment.
- **EJS include for CSS partials:** Use `<%- include('_partial-name') %>` (unescaped output `<%-`) for including EJS partials that contain HTML/CSS. The partial file name starts with underscore by convention (e.g., `_verdict-styles.ejs`). The partial has access to all template locals from the parent template (e.g., `verdict.category` works inside the included file). Note: EJS `include` paths are relative to the template's directory, not the project root.
- **Opus 4.6 may serialize nested tool_use fields as JSON strings:** When using `submit_*` tools with deeply nested schemas (like Strategist's `investigatorGuidance`), Opus sometimes returns a nested object as a JSON string instead of a parsed object. The Strategist agent now includes a recovery step that JSON-parses any string fields that look like JSON objects before Zod validation. If this pattern recurs in other agents, apply the same fix.
- **Pipeline error propagation semantics:** The pipeline only gracefully handles investigator failures (via `Promise.allSettled`). Classifier, Strategist, DA, and Judge failures propagate as thrown errors — there is no skip-and-continue logic for these agents. Resilience tests should verify this propagation behavior rather than assume graceful degradation for all agents. DB persistence is partial on failure: results are saved up to the point of failure (e.g., classifier result saved before strategist throws).
- **Confidence gate vs. Judge confidence semantics mismatch:** The confidence gates interpret the score as "truth likelihood" (85-100 = likely-true, 0-29 = likely-false), but the Judge produces confidence as "verdict confidence" (97 = 97% sure my verdict is correct). When the Judge says `likely-false` with 97% confidence, the gate overrides it to `likely-true`. This is a known design tension — future task should align the Judge's prompt to produce confidence as truth-likelihood, or invert the score for negative verdicts before gate enforcement.
- **E2E pipeline takes ~190s with real API calls:** The full pipeline with 6 agents (Haiku + Opus + 3×Sonnet + Opus + Opus) costs ~$0.50-0.60 and takes ~3 minutes. The Judge with effort "max" is the bottleneck (~60-90s for 3 turns). Integration test timeout must be ≥300s.
- **Investigator failures are common with real search APIs:** With real Brave/Google Fact Check search tools, 1-2 of 3 investigators may fail (e.g., text parse fallback fails if model doesn't call submit_report and text output doesn't match AgentReport schema). Pipeline continues gracefully with ≥1 report. Seed demo consistently gets 2-3 successful investigators out of 3.
- **Seed script env bootstrapping:** The seed script sets a dummy `TELEGRAM_BOT_TOKEN` env var when not present (required by `loadEnv()` Zod validation) since the bot isn't used during seeding. This avoids requiring a real bot token just to seed demo data.
- **Stale compiled `.js` files in `src/` break tests:** If `tsc` is run with the default `outDir` pointing into `src/` (or no outDir), compiled `.js` files land next to `.ts` sources. Vitest then resolves `.js` imports to the compiled CommonJS files instead of the `.ts` sources, causing `"exports is not defined in ES module scope"` and `"better_sqlite3_1.default is not a constructor"` errors. Fix: delete all `src/**/*.js` files. The `.gitignore` should exclude `src/**/*.js` to prevent recurrence.
- **Landing page EJS partial extraction for 400-line limit:** When `landing.ejs` exceeds 400 lines, extract sections into `_<section-name>.ejs` partials (e.g., `_verdict-preview.ejs`, `_opus-showcase.ejs`). EJS `<%- include('_partial-name') %>` renders the partial inline — tests that check for CSS classes or content in the rendered HTML work identically whether the section is inline or in a partial. No route changes needed.

- **Live page JS partial extraction pattern:** When `_live-agent-script.ejs` exceeds 400 lines, extract the verdict reveal logic into `_live-verdict-reveal.ejs` partial via `<%- include('_live-verdict-reveal') %>`. The partial has access to all variables from the enclosing `<script>` IIFE scope (e.g., `investigationId`, `elapsedTimer`) since EJS `include` inlines the content before browser execution. Same pattern as CSS partials — tests checking rendered HTML work identically.
- **Status text cycling for demo polish:** `startStatusCycle(statusElId, messages, intervalMs)` / `stopStatusCycle(statusElId)` functions cycle through micro-story status messages while agents are active. Uses `setInterval` with CSS opacity fade transition (0.2s). Call `stopStatusCycle` before setting final completion text. Keeps demo video visually alive during long agent waits (Strategist ~8s, DA ~10s, Judge ~5s).
- **Chat page reuses live page partials and styles:** `chat.ejs` includes both `_chat-styles.ejs` (chat-specific CSS) and `_live-styles.ejs` (agent card, progress bar, verdict reveal CSS) since it renders the same `_live-agent-cards.ejs` HTML partial inline. The JS agent update functions are duplicated in `_chat-sse-handlers.ejs` (not shared with `_live-agent-script.ejs`) because the chat page SSE is connected dynamically after POST success, whereas the live page connects on page load. Both pages connect to the same `/api/live/:id/stream` SSE endpoint.
- **Chat verdict reveal partial extraction:** `_chat-verdict-reveal.ejs` extracted from `_chat-sse-handlers.ejs` to keep it under 400 lines (same pattern as `_live-verdict-reveal.ejs`). Contains `CATEGORY_COLORS` map and `showVerdictReveal(data)` function. Includes manipulation technique pills (severity-colored: high ≥70 red, medium ≥40 amber, low gray) and Deep Reasoning badge. The partial has access to `investigationId`, `elapsedTimer`, and `escapeHtml` from the enclosing IIFE scope.
- **EJS template variable additions break multiple test files:** When adding a new template variable to `verdict.ejs` (or any shared EJS template), ALL test files that render that template must include the new variable in their `data` object — even if the test doesn't care about that variable. Three test files render `verdict.ejs`: `verdict-render.test.ts`, `verdict-sections.test.ts`, `verdict-details.test.ts`. EJS throws `ReferenceError: <var> is not defined` if the variable isn't provided and the template references it (even inside an `if` guard, since EJS evaluates the expression).
- **CSS class names in rendered HTML tests — check element, not class:** When testing that a conditional EJS block is NOT rendered, don't use `toContain("fc-class-name")` because CSS class names appear in the `<style>` block even when the HTML element is absent. Instead, check for the specific HTML element: `toContain('<div class="fc-class-name">')`.
- **NHK World URL times out at default 10s fetch timeout:** The test URL `https://www3.nhk.or.jp/nhkworld/en/news/20260215_03/` may time out from certain networks. The pipeline gracefully falls back to raw message text when URL extraction fails. E2E tests should tolerate both success and failure of URL extraction — validate the pipeline completes correctly in either path.
- **URL E2E pipeline takes ~230s with DA escalation:** When the pipeline processes a URL input where investigators disagree (spread > 30), DA escalates to "max" effort, adding ~100s. Combined with the 10s URL fetch timeout, the full URL pipeline E2E needs a 300s test timeout.
- **Grammy 409 conflict crashes Railway deployments:** When Railway deploys a new instance, the old bot may still be polling `getUpdates`. The new bot's `bot.start()` gets a 409 "terminated by other getUpdates request" error, which is an unhandled rejection that crashes the entire Node.js process (including Express). Fix: wrap `bot.start()` in a `.catch()` that detects 409 errors and retries with exponential backoff (5 retries, 3s base delay doubling each attempt). Express server stays alive even if bot fails permanently.
- **Strategist `investigatorGuidance` string serialization is intermittent:** Despite `deepParseJsonStrings` mitigation, the Strategist Zod validation can still fail when Opus returns `investigatorGuidance` as a JSON string. Observed in production (investigation `ajJ7QSatdg_y_RkUudHyy`). The `deepParseJsonStrings` function works correctly in isolation — the root cause may be related to how the Anthropic SDK serializes or freezes `toolUseBlock.input` in rare cases. The pipeline correctly catches the error and marks the investigation as failed (no server crash). Consider adding a retry with `JSON.parse` fallback directly on the `investigatorGuidance` field before Zod validation as a belt-and-suspenders fix.

- **Vitest 4 mock constructors require `function` syntax:** In Vitest 4, `vi.fn().mockImplementation(() => ({ ... }))` fails as a constructor because arrow functions lack `[[Construct]]`. Use `vi.fn(function () { return { ... }; })` with regular `function` syntax when mocking classes that will be called with `new`. This applies to `InvestigationPipeline`, `ClaudeClient`, `InvestigationRepository`, `ToolRegistry`, etc. in eval harness tests.
- **WhatsApp webhook signature must be verified BEFORE sending 200:** Meta's docs suggest responding 200 immediately, but signature verification must happen before the response — returning 200 for invalid signatures would acknowledge untrusted payloads. The webhook POST route verifies HMAC-SHA256 first, returns 403 on failure, then sends 200 only for valid payloads. Raw body is needed for accurate HMAC computation — captured via Express `verify` callback on `express.json()` middleware and stored as `req.rawBody`.

- **Investigator "contradicted" vs "mixed" assessment for exaggeration claims:** Before L5.1, investigators used "contradicted" for claims that exaggerated real research (e.g., "Harvard study proves chocolate prevents heart disease"). The binary framework had no way to express "kernel is true, framing is exaggerated." Adding explicit "mixed" assessment guidance to all 3 investigator prompts + partially-true reasoning to the Judge prompt fixed this — partial-001 moved from likely-false (10%) to partially-true (62%).
- **Classifier over-classifies vague urgency-framed messages as "other":** Before L5.1, messages like "BREAKING: The president just announced..." were classified as "other" and short-circuited, returning a generic response instead of an "unverified" verdict. Adding a rule for urgency framing ("BREAKING", "JUST IN", etc.) in the Classifier prompt routes these to `factual_claim` so the pipeline can return a substantive verdict.
- **Vague claims cause Judge timeout at 180s:** When adversarial-001 was reclassified from "other" to "factual_claim" (L5.1), the pipeline ran the full investigation but the Judge timed out after 180s. Vague claims produce investigators with no real evidence, and the Judge with effort "max" spends too long trying to evaluate nothing. May need a shorter timeout or reduced effort for vague claims in future.

- **`repo.create()` options-based API ripple effect:** Changing `InvestigationRepository.create()` from positional args `(msg, chatId?, msgId?, sourceUrl?)` to options-based `(msg, options?)` requires updating: (1) `src/orchestrator/pipeline.ts` caller, (2) `src/server/routes/investigate.ts` caller, (3) `src/server/routes/chat.ts` caller, (4) existing `investigation-repository.test.ts` assertions, (5) `pipeline.test.ts` mock assertions, (6) `pipeline-platform.test.ts` mock assertions. The investigate route test must also update its assertion from `telegram_chat_id` to `platform_chat_id` since the route no longer specifies a platform. Many other test files call `repo.create("text")` with single arg — those require no changes.

## Conventions

- **Env config testing pattern:** `loadEnv()` accepts an optional `env` record for testing. Pass env vars directly instead of manipulating `process.env` to avoid interference from `.env` file loading.
- **Investigator agent pattern:** All 3 investigators follow the same shape: `run*(claim, searchStrategy, client, toolRegistry)` → `{ report: AgentReport, costUsd }`. They use `runAgent` with maxTurns=4, inject search strategy guidance into the system prompt, use `submit_report` tool for structured AgentReport output, and fall back to text JSON parsing. Only the system prompt and tool set differ between investigators.
- **Shared test fixtures:** `tests/fixtures/` provides factory functions (`makeClassifierResult`, `makeSearchStrategy`, `makeAgentReport`, `makeChallengeReport`, `makeFinalVerdict`, `makeInvestigation`) and canned search results (`makeCannedBraveResults`, `makeCannedFactCheckResults`). Import from `tests/fixtures/index.js`. Each factory accepts `Partial<T>` overrides spread at top level; `makeSearchStrategy` does deep merge on nested objects (`claimCharacteristics`, `investigatorGuidance`, `falsificationCriteria`).

- **Eval code structure:** Eval suite lives in `eval/` (separate from `src/`), tests in `tests/unit/eval/`. Eval types use Zod schemas (same pattern as production schemas). Import eval modules in tests via relative path with `.js` extension (e.g., `import("../../../eval/dataset.js")`). `tsconfig.json` only includes `src/` but Vitest resolves `.ts` imports from `eval/` fine.
- **Eval claim ID convention:** Claim IDs use `{group}-{number}` format: `false-001`, `true-001`, `partial-001`, `nonfactual-001`, `adversarial-001`. Group prefix enables filtering by category in test assertions.

- **Eval canned search results pattern:** `eval/canned-results.ts` exports `getCannedResults(claimId)` → `{ brave: BraveSearchResult[], factCheck: FactCheckClaim[] }`. Loads from `eval/fixtures/{claimId}.json` with Zod validation (`CannedFixtureSchema`). Results cached in-memory after first load. `FACTUAL_CLAIM_IDS` constant lists the 12 factual claim IDs (Groups 1-3 + Group 5) that need canned results. `scripts/capture-eval-fixtures.ts` captures real API responses to seed/refresh fixtures (requires `BRAVE_SEARCH_API_KEY`; `GOOGLE_FACTCHECK_API_KEY` optional). Fixture files are committed to git as seed data.
- **Pipeline URL pre-processing uses `detectUrl` before `enrichMessageWithUrl`:** The pipeline calls `detectUrl(message)` first to check for a URL (pure sync function), then calls `enrichMessageWithUrl(message)` only if a URL was found. This enables emitting `url-fetch:start` with the URL *before* the async fetch begins, and `url-fetch:complete` with title/wordCount after extraction succeeds. If extraction fails, no `url-fetch:complete` event is emitted (graceful fallback). The `enrichMessageWithUrl` return type was extended to include `title` and `wordCount` (additive, non-breaking).

- **Pipeline intermediate outputs convention:** `InvestigateResult` includes optional `classifierResult`, `searchStrategy`, `agentReports`, and `challengeReport` fields. `classifierResult` is always populated (even for non-factual short-circuits). The other three are only present for factual claims that pass classification. Eval graders use these to evaluate each pipeline stage independently.
- **Eval harness pattern:** `EvalHarness` in `eval/harness.ts` runs claims through the pipeline with full isolation. Each claim gets a fresh `:memory:` SQLite DB. In mock mode, search tools return canned results from `eval/canned-results.ts` — pipeline agents (Classifier, Strategist, Investigators, DA, Judge) still make real LLM calls. In live mode, search tools call real APIs. `EvalTrialResult` captures verdict, all intermediate outputs, cost, duration, and errors. `EvalTrialResultSchema` Zod schema for serialization. Claims run sequentially with per-claim timeout via `Promise.race`.
- **Eval grader pattern:** Graders live in `eval/graders/`. Each grader exports a pure function `grade*(result: EvalTrialResult, claim: EvalClaim)` → typed grade object with Zod schema. Code-based graders (verdict, coverage) are sync; model-based graders (groundedness) are async. Each grader also exports an aggregate function for computing summary metrics across all grades. Non-factual claims handled separately from factual claims in verdict grading — non-factual checks classifier routing, factual checks verdict category + confidence + findings + sources.
- **Eval runner pattern:** `eval/run-eval.ts` is both an importable module and a CLI script. Exports `parseArgs(argv)` and `runEval(args)` for testability. Main module guard (`process.argv[1]?.endsWith("run-eval.ts")`) prevents execution when imported in tests. `EvalResult` type bundles all trial results, grade arrays, and aggregate summaries. Console summary and JSON file output are side effects of `main()`, not `runEval()`. npm scripts: `eval` (quick: mock + skip-groundedness), `eval:full` (mock + all graders), `eval:live` (real APIs).
- **Eval report pattern:** `eval/report.ts` exports `generateSummaryString(result, config)` → plain text console summary and `generateMarkdownReport(result, config)` → markdown string with per-claim table, metrics tables, and failures list. `saveMarkdownReport(result, config)` writes to `eval/results/eval-{timestamp}.md`. `ReportConfig` interface takes `mode` string. Failures collected and sorted by harm weight descending in both summary and markdown. `run-eval.ts` delegates console printing to `generateSummaryString` and saves both JSON and markdown reports.

- **Platform directory barrel exports:** Each platform subdirectory (`src/platforms/telegram/`, `src/platforms/whatsapp/`) has an `index.ts` barrel export re-exporting the adapter, responder, and formatter. Import from the barrel (e.g., `from '../platforms/telegram/index.js'`) for external consumers; use direct file imports (e.g., `from './formatter.js'`) within the platform directory.
- **Telegram formatter moved to platform directory:** `src/formatter/telegram-formatter.ts` → `src/platforms/telegram/formatter.ts`. The `src/formatter/` directory now only contains platform-agnostic code (`confidence-gates.ts`). Platform-specific formatters live alongside their adapter and responder.

## Decisions Log

- **Task 0.1:** Used `noUncheckedIndexedAccess: true` in tsconfig for extra safety on array/object indexing. Used `isolatedModules: true` for compatibility with transpilers. Vitest config kept minimal — no globals, file pattern `tests/**/*.test.ts`.
- **Task 0.2:** Installed all production deps. Zod resolved to v4 (4.3.6) — API is backward-compatible with spec schemas. Express resolved to v5 (5.2.1). All 9 production packages + 3 dev type packages installed and importable.
- **Task 0.3:** Env config uses Zod for validation with `loadEnv(env?)` pattern. `dotenv.config()` called inside `loadEnv()` only when no custom env is provided. Added `dotenv` as production dependency. `.env.example` already existed from prior setup.
- **Task 0.4:** Logger uses `createLogger(options?)` factory pattern with `LoggerOptions` interface (`level`, `pretty`). Pretty printing via pino `transport` config (not the deprecated `prettyPrint` option). Defaults to `info` level and JSON output. Consumers will call `createLogger({ level: config.LOG_LEVEL, pretty: config.NODE_ENV === "development" })`.
- **Task 1.1:** Database connection uses `createDatabase(dbPath)` factory function. Enables WAL mode and foreign keys via pragmas. Auto-creates parent directories with `mkdirSync(dirname(dbPath), { recursive: true })`. Tests use `os.tmpdir()` with random UUIDs for isolation, and clean up `-wal`/`-shm` files in afterEach.
- **Task 1.2:** Migrations use `runMigrations(db)` with `CREATE TABLE IF NOT EXISTS` for idempotency. All JSON columns (classifier_result, search_strategy, agent_reports, challenge_report, final_verdict) use the `JSON` column type — stored as TEXT in SQLite but semantically typed. Default values: `status='pending'`, `created_at=datetime('now')`, `total_cost_usd=0`.
- **Task 1.3:** `InvestigationRepository` class wraps better-sqlite3 with typed CRUD methods. JSON columns serialized with `JSON.stringify()` on write, `JSON.parse()` on read. Uses `nanoid()` for ID generation (21-char default). `getRecent()` orders by `rowid DESC` instead of `created_at DESC` because `datetime('now')` has second-level granularity — multiple inserts within the same second get identical timestamps.
- **Task 3.1:** `ClaudeClient` class wraps Anthropic SDK with `createMessage()` and `estimateCost()`. Pricing: Haiku $1/$5, Sonnet $3/$15, Opus $5/$25 per MTok (input/output). Thinking tokens billed as output tokens. Exposes `_client` getter for test mocking — assign `client._client.messages.create` directly. QA test uses `it.skipIf(!apiKey)` to auto-skip when no API key is set. `MODELS` constant exported with all 3 model IDs.
- **Task 3.2:** `runAgent(config)` function implements the core agentic tool-use loop. Uses `Promise.race` for timeout enforcement (not AbortController signal — mocks don't respect it). Internal `runAgentLoop()` handles the multi-turn loop: calls `client.createMessage()`, checks for `tool_use` blocks, executes tools via `onToolCall` callback, pushes assistant content + tool results to messages array, loops until `stop_reason !== "tool_use"` or maxTurns reached. Tool errors are caught and returned as `is_error: true` tool_result blocks (never thrown). Thinking config passed through to API. Token usage and cost accumulated across turns. `ContentBlockParam` requires cast from `response.content` due to SDK type narrowing.
- **Task 4.1:** `braveWebSearch(query, count, apiKey)` function wraps the Brave Search API. Returns `{ results: BraveSearchResult[] }` with `title`, `url`, `description`, `age` fields. API key passed as parameter (not read from env directly) so tool registry can inject it. Graceful error handling: returns `{ results: [] }` on HTTP errors or network failures. `braveSearchToolDefinition` exported as a Claude `Tool` type for agent tool configs. Tests mock global `fetch` via `vi.stubGlobal("fetch", mockFn)`.
- **Task 4.2:** `googleFactCheckSearch(query, apiKey)` function wraps the Google Fact Check Tools API (`v1alpha1/claims:search`). Returns `{ claims: FactCheckClaim[] }` with `text`, `claimant`, and `claimReviewMarkup` (containing `url`, `title`, `publisher`, `rating`). Follows same pattern as Brave Search: API key as parameter, graceful error handling returning `{ claims: [] }`. Claims without `claimReview` arrays are filtered out. When a claim has multiple reviews, uses the first one. `googleFactCheckToolDefinition` exported for Claude tool configs.
- **Task 4.3:** `ToolRegistry` class maps tool names to handlers and Claude tool definitions. Methods: `register(name, handler, definition)`, `execute(name, input)` → `Promise<string>`, `getToolDefinitions()` → `Tool[]`. Unknown tools return error strings (not thrown).
